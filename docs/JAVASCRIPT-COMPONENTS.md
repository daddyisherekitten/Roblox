# Shadow DOM and custom elements

Component nodes use the same data DOM, stylesheet resolver, retained rendering boxes, input model, script VM and event loop as ordinary HTML. Shadow trees are not separate copies of the page. Light DOM ownership stays separate from the flat tree used for painting and slot distribution.

Implemented interfaces:

- `Element.attachShadow({mode, delegatesFocus, slotAssignment, clonable, serializable, customElementRegistry})`, open/closed `shadowRoot`, `slot`, `assignedSlot`, `getRootNode({composed})` and shadow-inclusive connectivity.
- `ShadowRoot.host`, `mode`, `delegatesFocus`, `clonable`, `serializable`, `slotAssignment`, `innerHTML`, scoped query methods, `getElementById`, `activeElement`, `styleSheets` and `adoptedStyleSheets`.
- Named/default/manual slot distribution; `HTMLSlotElement.assign`, `assignedNodes`, `assignedElements`, fallback flattening and coalesced `slotchange` microtasks. Distribution updates after children, slot names and slottable `slot` attributes change.
- Composed event paths, host retargeting, host event phase, closed-root path filtering, slotted event paths and listener-specific `relatedTarget`/touch target retargeting.
- Scoped shadow styles, `:host`, `:host(compound)`, `:host-context(compound)`, host descendant selectors, qualified `slot::slotted(compound)`, `::part(name...)`, nested `exportparts` mappings and independent root stylesheet sources. Supported host/slot/part selectors also survive constructed-sheet parsing before adoption. Normal declarations win from outer scopes; important declarations win from inner scopes, including inline declarations in their own scope.
- Global `customElements` and constructible scoped `CustomElementRegistry` instances with `define`, `get`, `getName`, `whenDefined`, `upgrade` and `initialize`. Root parsing, `createElement` options and null-registry initialization retain each element's registry independently of its eventual flat-tree render parent. Autonomous and customized built-in HTML elements use native `HTMLElement`/specialized HTML constructor chains; class fields, private fields and accessors remain on stable DOM wrappers.
- Definition-time callback/observed-attribute snapshots, construction stacks, failed upgrade state, connected/disconnected and observed attribute reactions. Reactions retain their order across constructor mutations; exceptions are reported without replacing the page.
- `adoptedCallback` receives the old/new retained document wrappers; `moveBefore` preserves the component connection and invokes `connectedMoveCallback`, with disconnected/connected fallback when that callback is absent. Form-owner reactions still follow the native browser's temporary removal/reinsertion behavior.
- Adoption between live JavaScript runtimes retains the original wrapper, prototype and existing custom definition. Scoped registries retain their identity and later definitions also upgrade eligible nodes in the adopted document; global/null registries use the destination effective global registry. Registry brands are host-created and shared between live bridges. Cloning uses the retained scoped registry or substitutes the destination global registry, and runs constructors/reactions in the resulting definition's realm after attributes and clonable shadow trees are copied. Adopted internals validity/state paint, invalid-event propagation and validation reporting use the destination document's host.
- `HTMLElement.attachInternals`, branded `ElementInternals`, live `ValidityState`, `CustomStateSet` and `:state()` selectors. Internals expose an attached closed shadow root to its component, default ARIA values and element relationships without reflecting those defaults into author attributes.
- Form-associated autonomous elements supply nullable string/File/FormData values through `setFormValue`. FormData entry lists are copied immediately. Ordinary form collection, submission, validity, disabled fieldset/first-legend rules and reset delegate to the same component record. Validation anchors can point into nested shadow trees, and the cancelable `invalid` event is dispatched at the custom host.
- Ordered-list/list-item reflected attributes and native prototype descriptors keep signed integer defaults/conversion, boolean presence and string reflection in the ordinary mutation path.
- Native table interface prototype methods/accessors delegate to the ordinary table DOM bridge with the appropriate receiver brands.

`ShadowRoot` inherits `DocumentFragment`: inserting it moves its children into the destination while the emptied root remains attached to its host. Clonable shadow trees copy their root options and child DOM. Closed roots remain unavailable through the public host getter while their retained raw root still participates in rendering and event dispatch.

## Captured browser profile

The R03 browser fixture records Chromium 154 behavior. Two cases currently differ from the October 2026 HTML Living Standard text: this browser accepts an `extends` option in a scoped registry, and `setValidity` rejects an invalid validation anchor before changing existing constraint flags/message. The engine follows these measured browser results and retains the differences in the fixture rather than claiming both algorithms are identical. The browser also accepts Unicode and punctuation in otherwise valid custom-element local names under the current DOM name grammar. Its live CustomStateSet iterators can observe a subsequent add after returning `done:true`; the captured case preserves this behavior separately from ordinary JavaScript Set iterators.

`tests/fixtures/javascript-r03-realms-browser.json` captures the two-frame registry/adoption probe. An imperative root created with `customElementRegistry:null` gains the destination global registry when adopted; its cloned root also uses that registry. Chromium retains null registries on the original null-root descendants and their clones, while a separately adopted explicit-null element gains the destination global registry. The engine uses an operation-local snapshot of the original shadow registry for this measured descendant case; it does not permanently mark imperative roots as keeping null. The Standard's `keep custom element registry null` flag belongs to declarative roots with `shadowrootcustomelementregistry`, and is copied when those roots are cloned. This distinction is part of the captured profile, rather than a claim that Chromium executes the Standard's preorder adoption algorithm unchanged.

## CSS registration and list profile

`@property` registrations apply throughout a document, including declarations sourced from shadow roots. Supported typed grammars are `<length>`, `<length-percentage>`, `<percentage>`, `<number>`, `<integer>`, `<color>`, `<string>` and `<custom-ident>`, literal alternatives, unions and `+`/`#` lists. Types outside this set are diagnosed. Initial values, inheritance flags, invalid/cyclic values, final-font-size relative lengths and supported math are computed before substitution. Counter-style names remain tree scoped; text symbols support cyclic, fixed, symbolic, alphabetic, numeric, additive and extends systems, anonymous `symbols()` and literal marker strings. Image symbols and the complete predefined language-counter set remain outside this profile.

Ordinary ordered-list markers use HTML ordinal values: `start`, rendered owned items, `reversed` and `li[value]` retain the native browser numbering. Explicit CSS counter reset/increment/set and authored `counter()`/`counters()` content use the CSS counter scope algorithm. In particular, an ordinary reversed three-item list with its second item `value="7"` has markers `3,7,6`; the CSS automatic `reversed(list-item)` counter before that value hint starts at `8`.

The captured Chromium does not yet map every HTML value/reversed hint into authored `counter(list-item)` content. The native reference fixture deliberately shows decimal markers next to the authored counter value rather than treating them as interchangeable. The engine keeps native HTML markers and the documented CSS algorithm separate in these cases. [HTML ordinal values](https://html.spec.whatwg.org/multipage/grouping-content.html#ordinal-value), [HTML CSS presentational hints](https://html.spec.whatwg.org/multipage/rendering.html#lists) and [CSS implicit list-item counters](https://drafts.csswg.org/css-lists-3/#list-item-counter) specify the corresponding algorithms; `tests/fixtures/css-combination-reference.html` records the comparison.

## Current limits

Declarative root adoption is available for parser-created declarative roots; Trusted Types, `getHTML`/`setHTML` serialization policies and all new serializable-root APIs are outside this implementation. ARIA defaults have the correct DOM-facing values, but this component layer does not provide an operating-system accessibility tree for Roblox. Component state-restoration callbacks are supplied through the host adapter; this does not by itself persist arbitrary component state between game sessions.

The engine implements the tested component construction, upgrade and retained-registry clone/adoption paths, but does not claim the complete browser prototype surface for every specialized HTML interface or every browser lifecycle edge case. Cross-realm components require both host runtimes to remain alive; disposing their originating VM is not equivalent to an ordinary browser navigation that keeps reachable realm objects alive. Cross-realm File/FormData union conversion still requires shared network-data branding; the two-runtime component cases verify string submissions, and binary values are verified in their originating realm. Native font rasterization, Roblox control appearance and unsupported CSS effects remain renderer limitations rather than component-specific substitutions.

The algorithms follow the primary [DOM Standard](https://dom.spec.whatwg.org/#shadow-trees) and [HTML custom-elements specification](https://html.spec.whatwg.org/multipage/custom-elements.html). Native reference results identify the browser behavior actually exercised; they do not imply complete standards conformance.
